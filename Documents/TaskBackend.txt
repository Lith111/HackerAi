# خطة عمل الباك إند مقسمة إلى 6 مهام (Tasks)

### المهمة 1: تأسيس المشروع ونظام المستخدمين والمصادقة (Project Foundation & Authentication)

**الهدف:** بناء العمود الفقري للمشروع، إعداد البيئة، وإنشاء نظام مستخدمين آمن بصلاحيات مختلفة.

**الدخل (Input):**
- متطلبات النظام الموثقة (أدوار المستخدمين: طالب، مدير).
- قرار استخدام Django, DRF, PostgreSQL, JWT.
- صورة واضحة عن مسارَي التعلم (Red/Blue) المرتبطين بالمستخدم.

**الخرج (Output):**
- مشروع Django يعمل وقابل للتشغيل محلياً.
- قاعدة بيانات PostgreSQL مُنشأة ومُهاجرة بالنماذج الأولية.
- نظام تسجيل وتسجيل دخول كامل عبر REST API (JWT).
- صلاحيات جاهزة للتطبيقات الأخرى.
- توثيق أولي تلقائي للـ API.

**المهام التفصيلية (Tasks Checklist):**
1.  إنشاء بيئة افتراضية وتثبيت `Django`, `DRF`, `psycopg2`, `djangorestframework-simplejwt`, `django-cors-headers`, `drf-spectacular`.
2.  إنشاء مشروع Django (`config/`) وتطبيق `accounts/`.
3.  إعداد `settings.py` (قاعدة البيانات، اللغة، التوقيت، تثبيت التطبيقات المطلوبة).
4.  تمديد نموذج `User` المدمج (أو نموذج مخصص) لإضافة حقل `role` (`student`, `admin`) وحقل `learning_path` (`red_team`, `blue_team`).
5.  كتابة `managers` و`serializers` لتسجيل المستخدمين مع اختيار المسار.
6.  إعداد نظام مصادقة JWT (تسجيل الدخول يعيد `access` و`refresh`).
7.  بناء واجهات API:
    - `POST /api/auth/register/`
    - `POST /api/auth/login/`
    - `GET /api/auth/me/`
8.  كتابة صلاحيات DRF مخصصة (`IsAdmin`, `IsStudent`, `IsOwner`) لاستخدامها لاحقاً.
9.  ضبط `CORS` ليسمح بطلب واجهة React.
10. إعداد `drf-spectacular` لتوليد وثائق Swagger تلقائية.
11. إجراء اختبارات وحدة (Unit Tests) لنماذج المستخدم والمصادقة.

### المهمة 2: نظام المحتوى التعليمي وإدارة الدروس (Courses & Content Management)

**الهدف:** بناء هيكل تخزين الدروس بأقسامها الأربعة، وتوفير API لإدارتها وعرضها.

**الدخل (Input):**
- نموذج الدرس المكون من 4 كتل (شرح الثغرة، كود الاستغلال، نظرية الحماية، كود الحماية).
- صلاحيات المستخدمين من المهمة 1.
- طلب دعم Markdown أو نصوص غنية للمحتوى.

**الخرج (Output):**
- جداول دروس وكُتل جاهزة في قاعدة البيانات.
- نظام CRUD كامل للمدير لإدارة الدروس.
- واجهة API لعرض الدروس المتاحة للطالب مع محتوى كتلها.
- إمكانية ترتيب الدروس وتحديد المسار (أحمر/أزرق) عبر API.

**المهام التفصيلية:**
1.  إنشاء تطبيق `courses/`.
2.  تصميم النماذج:
    - `Lesson`: (title, slug, order, path, is_published ...).
    - `LessonBlock`: (lesson FK, block_type اختيار من `VULN_THEORY`, `EXPLOIT_CODE`, `DEFENSE_THEORY`, `SECURE_CODE`, content TextField, code_snippet TextField, language).
3.  إعداد `serializers` لـ `Lesson` و`LessonBlock` (متداخلة أو منفصلة).
4.  بناء نقاط نهاية API للمدير (تتطلب صلاحية `IsAdmin`):
    - `POST /api/admin/courses/` لإنشاء درس.
    - `PUT /api/admin/courses/{slug}/` لتعديل درس وكتله.
    - `DELETE /api/admin/courses/{slug}/`.
5.  بناء نقاط نهاية API للطالب:
    - `GET /api/courses/` (تعيد قائمة الدروس المتاحة بناءً على مسار الطالب، مع معلومات عن حالة القفل).
    - `GET /api/courses/{slug}/` (تعيد الدرس وكتله الأربعة).
6.  إضافة منطق ترتيب الدروس (`order` field) وعرضها في الاستجابة.
7.  كتابة `Admin Site` مخصص أو استخدام DRF Browsable API.
8.  اختبارات للتأكد من أن الطالب لا يمكنه تعديل درس، وأن المدير يمكنه ذلك.

### المهمة 3: نظام تتبع التقدم والتسلسل القسري (Progress & Sequencing)

**الهدف:** فرض التعلم المتسلسل، وتخزين حالة تقدم كل طالب لكل درس بدقة (أي كتلة أنجزها)، وتوفير نقاط API لتحديث التقدم وعرض الإحصائيات.

**الدخل (Input):**
- تطبيق الدروس جاهز (المهمة 2).
- صلاحيات المستخدم.
- اشتراط عدم إكمال الدرس إلا بعد إكمال جميع كتله الأربعة.

**الخرج (Output):**
- آلية قفل / إظهار الدروس التلقائية بناءً على تقدم الطالب.
- نقاط نهاية API تُمكّن الواجهة الأمامية من تسجيل إتمام كتلة وتحديث التقدم العام.
- بيانات إحصائية (نسبة الإنجاز) للمستخدم تظهر في لوحة التحكم.

**المهام التفصيلية:**
1.  إنشاء تطبيق `progress/`.
2.  تعريف نموذج `StudentProgress`:
    - `user` (FK), `lesson` (FK)، مع `unique_together`.
    - `completed_blocks` (ArrayField أو JSONField يحمل أسماء الكتل المكتملة مثل `["VULN_THEORY", "EXPLOIT_CODE"]`).
    - `is_lesson_completed` (Boolean، يُحسب تلقائياً أو يُحدّث).
3.  كتابة دالة خدمة (Utility) تتحقق من أن المستخدم أكمل الدرس السابق (حسب `order`) قبل أن يسمح له بالوصول للدرس التالي. تستخدم في `GET /api/courses/` لحساب `is_locked`.
4.  بناء نقطة نهاية لتحديث التقدم:
    - `POST /api/progress/lessons/{id}/complete-block/` (تستقبل `block_type`، تتحقق من صحته، تضيفه للمصفوفة، وإذا اكتملت الأربعة تُعين `is_lesson_completed=True`).
5.  بناء نقطة نهاية لعرض التقدم الإجمالي:
    - `GET /api/progress/` (تعيد كل سجلات تقدم الطالب الحالي مع تفاصيل الدرس، ونسبة مئوية عامة).
6.  دمج منطق التسلسل في استجابة `GET /api/courses/`: كل درس يُرفق معه حقل `is_locked: true/false`.
7.  التأكد من أن الطالب لا يستطيع استدعاء واجهة `complete-block` لدرس لم يكمله بالترتيب (إضافة حماية خلفية إضافية).
8.  اختبار سيناريوهات القفل والتسلسل.

### المهمة 4: مختبر التيرمنال الوهمي ونظام الاختبارات عبر WebSocket (Lab Simulator)

**الهدف:** تطوير قلب المنصة التفاعلي، حيث يخوض الطالب اختبارات محاكاة التيرمنال، مع محرك مطابقة أوامر، ونظام مساعدة مؤقتة باستدعاء الذكاء الاصطناعي (سيتم ربطه في المهمة 5).

**الدخل (Input):**
- نماذج السيناريوهات والأوامر المطلوبة.
- تثبيت `Django Channels` و RabbitMQ (أو طبقة خلفية قاعدة بيانات).
- تقدم الطالب (المهمة 3) لتحديد الأهلية للاختبار.
- واجهة React ستقوم بفتح WebSocket.

**الخرج (Output):**
- خدمة WebSocket تعمل على مسار `ws/terminal/{session_id}/`.
- آلية بدء جلسة اختبار، استقبال أوامر، مطابقة Regex، إصدار ردود.
- منطق "الأمر الخاطئ" وظهور خيار المساعدة المؤقتة.
- تحديث حالة الجلسة في قاعدة البيانات (يمكن استئنافها أو إعادة تعيينها).
- بنية تحتية جاهزة لاستقبال تدخل الذكاء الاصطناعي (المهمة 5).

**المهام التفصيلية:**
1.  إعداد `Django Channels` وطبقة خلفية (مثال: `database_redis` أو تثبيت `channels_rabbitmq` واستخدام RabbitMQ). تسجيل تطبيق `lab/`.
2.  تعريف نماذج `LabScenario` (title, description, learning_path) و `LabCommand` (scenario FK, input_regex, expected_output, step_order).
3.  تعريف نموذج `TerminalSession`:
    - `user`, `scenario`, `current_step` (افتراضي 1), `command_log` (JSONField)، `is_active`, `ai_help_text`, `help_activated_at` (DateTime).
4.  كتابة `routing.py` للـ WebSocket وربطه بـ `Consumer`.
5.  بناء `LabConsumer` (AsyncJsonWebsocketConsumer أو SyncConsumer):
    - عند الاتصال: تحقق من JWT عبر `TokenAuthMiddleware`، تحميل الجلسة من DB أو إنشائها.
    - عند استقبال رسالة `{"command": "..."}`:
        - استرجاع `LabCommand` التالي بناءً على `current_step` و`scenario`.
        - مقارنة `command` باستخدام `re.match(pattern, command)`.
        - إذا تطابق: إرسال `{"output": expected_output}`، وزيادة `current_step`، وتسجيل في `command_log`.
        - إذا لم يتطابق: إرسال `{"output": "command not found", "help_available": true}`، مع تحديث عداد الأخطاء.
    - رسالة خاصة لطلب المساعدة: عندما يرسل العميل `{"action": "request_help"}` (أو تستخدمها الواجهة بعد موافقة المستخدم)، يقوم الـ Consumer بإنشاء مهمة Celery لاستدعاء AI (تُركب في المهمة 5) أو يديرها مباشرة بشكل متزامن خفيف.
6.  بناء آلية إعادة التعيين (Reset): عند أمر `{"action": "reset"}`, قم بتصفير `current_step` ومسح `command_log`، وإعادة جلسة جديدة.
7.  بناء نقطة REST مساعدة:
    - `POST /api/lab/scenarios/{id}/start/` (تنشئ TerminalSession جديدة وتعيد session_id).
    - `GET /api/lab/scenarios/` (قائمة السيناريوهات).
8.  اختبار يدوي باستخدام متصفح WebSocket بسيط أو أداة اختبار.

### المهمة 5: تكامل الذكاء الاصطناعي (AI Integration)

**الهدف:** ربط المنصة بخدمة OpenAI لتقديم الشات بوت العام، وتنفيذ المساعدة المؤقتة داخل الاختبار بمحتوى يظهر 10 ثواني.

**الدخل (Input):**
- مكتبة `openai` ومفتاح API سري.
- محددات هندسة التوجيه (System Prompts) للشات بوت وللمساعد المؤقت.
- إعدادات Celery + RabbitMQ لتشغيل المهام بشكل غير متزامن.
- نموذج TerminalSession من المهمة 4.

**الخرج (Output):**
- شات بوت يعمل عبر REST API ويجيب على أسئلة الطلاب.
- عند طلب المساعدة في التيرمنال، يتم إرسال سجل الأوامر إلى ChatGPT ويعاد الرد مباشرة ليُعرض في الواجهة.
- الرسالة تختفي بعد 10 ثواني (يدار بالواجهة، لكن الخلفية توفر النص).
- طبقة حماية ضد Prompt Injection.

**المهام التفصيلية:**
1.  إنشاء تطبيق `ai/`.
2.  إعداد ملف `prompts.py` يحتوي على `SYSTEM_PROMPT_CHATBOT` يمنع إعطاء إجابات اختبار مباشرة، و `SYSTEM_PROMPT_HELP` يوجه النموذج لإعطاء حلول خطوة بخطوة.
3.  بناء نموذج `ChatLog` (اختياري لتخزين المحادثات).
4.  كتابة دالة `ask_chatbot(user_message, conversation_history)` باستخدام `openai.ChatCompletion`.
5.  نقطة نهاية `POST /api/ai/chatbot/` (تستقبل رسالة وتعيد رد الذكاء الاصطناعي).
6.  كتابة مهمة Celery: `provide_lab_help(session_id)`:
    - تسترجع `TerminalSession` من DB.
    - تجمع `command_log` وتحوله إلى نص.
    - ترسل prompt مخصص للذكاء الاصطناعي مع السجل.
    - تحفظ الرد في حقل `ai_help_text` في الجلسة.
    - ثم ترسل عبر WebSocket رسالة `{"action": "show_help", "help_text": "..."}` للمستخدم. (تحتاج إلى استخدام Channel Layers لإرسال رسالة إلى مجموعة WebSocket خاصة بالجلسة).
7.  ربط Consumer من المهمة 4 مع القناة الخاصة بالجلسة لاستقبال رسالة `show_help` وإعادة إرسالها للعميل.
8.  تعديل Consumer بحيث عندما تأتي رسالة `request_help`، يتحقق من عدم وجود طلب سابق، وينشئ مهمة Celery `provide_lab_help.delay(session_id)`.
9.  إعداد `Celery` مع RabbitMQ في `settings.py` و`celery.py`.
10. اختبار سيناريو المساعدة من البداية للنهاية: أمر خاطئ، طلب مساعدة، ظهور الرد، ثم إعادة التعيين بعد 10 ثواني من جهة الواجهة.

### المهمة 6: لوحة تحكم المدير، الأمان، الاختبارات النهائية والنشر (Admin Dashboard, Security, Testing & Deployment)

**الهدف:** توفير واجهات إدارية قوية، تأمين التطبيق، كتابة اختبارات شاملة، وإعداده للإطلاق في بيئة إنتاجية.

**الدخل (Input):**
- جميع التطبيقات السابقة تعمل.
- متطلبات لوحة تحكم المدير (إحصائيات، إدارة مستخدمين، إدارة سيناريوهات).
- بيئة إنتاج مستهدفة (خادم Linux، اسم النطاق).

**الخرج (Output):**
- نقاط نهاية API للوحة تحكم المدير مع إحصائيات.
- تغطية اختبارية واختبارات أمان.
- إعدادات إنتاج جاهزة (Gunicorn + Daphne + Nginx).
- تطبيق منشور وآمن.

**المهام التفصيلية:**
1.  بناء نقاط نهاية خاصة بالمدير (تطبيق `reports/` أو ضمن `accounts/`):
    - `GET /api/admin/dashboard/` تعيد: إجمالي الطلاب، تقدم كل طالب، إحصائيات النشاط.
    - `GET /api/admin/students/` لإدارة المستخدمين (تفعيل/تعطيل، تغيير المسار).
    - `GET /api/admin/student/{id}/progress/` لعرض تقدم طالب محدد.
2.  كتابة صلاحيات DRF قوية تضمن عدم وصول طالب لأيٍ من هذه.
3.  تنفيذ Throttling (تحديد المعدل) على نقاط الذكاء الاصطناعي والتيرمنال.
4.  كتابة اختبارات شاملة:
    - اختبارات وحدة لـ WebSocket Consumer (باستخدام `ChannelsLiveServerTestCase` أو `pytest-asyncio`).
    - اختبارات REST API مع محاكاة أدوار المستخدمين.
    - اختبارات أمنية: محاولة الوصول لنقاط غير مصرح بها، حقن SQL، اختبار Cross-Site.
5.  مراجعة إعدادات الأمان: `SECURE_SSL_REDIRECT`, `HSTS`, `CSRF` (تعديلها لتعمل مع JWT و SPA).
6.  إعداد بيئة الإنتاج:
    - تثبيت `Gunicorn` (WSGI) و `Daphne` (ASGI لـ Django Channels).
    - إعداد `Nginx` كوكيل عكسي يمرر طلبات WebSocket لـ Daphne.
    - إعداد `Supervisor` أو `systemd` لتشغيل العمليات (Daphne, Gunicorn, Celery worker, Celery beat إن لزم).
    - جمع الملفات الثابتة.
7.  إعداد متغيرات البيئة على السيرفر (`.env`).
8.  نشر أولي، فحص الوظائف، ومراقبة السجلات.
